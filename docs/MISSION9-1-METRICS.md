# 미션 9-1 — 지표 설계

> 대상 서비스: **linkple 채용 공고 MVP**(미션 5~8 누적) · 배포본 https://linkple-mission8.vercel.app
> 작성 2026-09-30 · Amplitude 프로젝트 `linkple-mission9` · GA4 `G-8B4G6MFMPW` · 짝 문서 [Tracking Plan](./MISSION9-1-TRACKING-PLAN.md)

---

## 1. 이 서비스는 양면이다 — 그래서 퍼널도 둘이다

| 이해관계자 | 서비스에서 하는 일 | 가치를 받는 순간 |
|---|---|---|
| **구직자** | 공고를 찾고 지원한다 | **지원이 접수된 순간** |
| **구인자** | 공고를 올린다(AI 초안 도우미 사용) | **공고가 게시된 순간** |

⛔한 퍼널로 합치지 않는다. 두 축은 **다른 화면·다른 행동**이고, 합치면 어느 쪽이 막혔는지 알 수 없다.

---

## 2. 핵심 지표(북극성) — 지원 제출 전환율

**정의 = 기간 내 `apply_submitted` 를 낸 사용자 수 ÷ 방문자 수**

왜 이것인가:
- 이 서비스가 존재하는 이유는 「공고를 본다」가 아니라 **「지원이 오간다」**다. 공고 열람은 그 앞 단계다.
- **구인자의 가치도 여기서 나온다** — 지원이 0건이면 공고를 올릴 이유가 없다. 양면 중 한쪽을 북극성으로
  고르면 나머지가 종속되는데, 이 서비스에서는 **지원이 그 축**이다.
- 서버 저장이 성공한 시점에만 측정한다. ⛔「지원하기 버튼 클릭」은 의도이고 가치 수령이 아니다.

⚠️**목표값은 지금 정하지 않는다.** 기준선이 없는 상태의 목표는 짐작이다. 미션 9-1 로 2주간
기준선을 측정하고, 미션 9-2 에서 그 분포를 보고 목표를 정한다.

## 3. 퍼널 — 북극성까지 가는 길

### 3-1. 구직자 퍼널(주)

```
방문 → 공고 목록 → 공고 상세 → (로그인) → 지원 시작 → ★지원 제출
```

| 단계 | 지표 | 산식 | 이 단계가 말해주는 것 |
|---|---|---|---|
| 1 | **방문자 수** | `page_view` 를 낸 순 사용자 | 유입 규모(채널별로 쪼갠다) |
| 2 | **목록 진입률** | `job_list_viewed` / 방문자 | 첫 화면이 「공고를 보러 가게」 만드는가 |
| 3 | **상세 열람률** | `job_detail_viewed` / `job_list_viewed` | 목록에서 고를 만한 공고가 있는가 |
| 4 | **로그인 통과율** | `login_completed` / `apply_started`(비로그인) | 로그인 벽에서 얼마나 빠지는가 |
| 5 | **지원 착수율** | `apply_started` / `job_detail_viewed` | 상세를 본 뒤 지원할 마음이 드는가 |
| 6 | ★**지원 완주율** | `apply_submitted` / `apply_started` | 지원서 작성이 어렵지 않은가 |
| — | ★**북극성** | `apply_submitted` / 방문자 | 전 구간 종합 |

### 3-2. 구인자 퍼널(보조)

```
방문 → 로그인 → 공고 작성 진입 → (AI 초안 요청 → 초안 채택) → ★공고 게시
```

| 단계 | 지표 | 산식 | 이 단계가 말해주는 것 |
|---|---|---|---|
| 1 | **작성 진입률** | `job_new_opened` / `login_completed`(구인자) | 로그인 후 공고를 올리러 가는가 |
| 2 | **AI 초안 사용률** | `ai_draft_requested` / `job_new_opened` | 도우미를 발견하고 쓰는가 |
| 3 | **AI 초안 채택률** | `ai_draft_accepted` / `ai_draft_requested` | 초안이 쓸 만한가(실패·이탈 포함) |
| 4 | ★**공고 게시율** | `job_posted` / `job_new_opened` | 작성을 끝까지 하는가 |
| — | **AI 기여도** | `job_posted`(used_ai=true) / `job_posted` 전체 | 미션 8 기능이 실제로 결과를 바꿨는가 |

## 4. 유입 분석(GA4) — 채널을 어떻게 가르는가

| 축 | 값 | 어디서 |
|---|---|---|
| 채널 | `utm_source`(kakao · naver_blog · instagram …) | URL 파라미터 |
| 방식 | `utm_medium`(sns · blog · dm) | URL 파라미터 |
| 캠페인 | `utm_campaign`(mission9_launch) | URL 파라미터 |
| **소재** | `utm_content`(생성형 AI 로 만든 이미지·문구 종류) | URL 파라미터 |

★**소재까지 구분한다**(심화 요구) — 같은 채널에서도 어떤 그림·문구가 먹히는지가 다음 홍보를 바꾼다.
UTM 은 **첫 진입 쿼리에만** 있으므로, 코드가 첫 값을 저장해 이후 이벤트에도 함께 싣는다
(`src/lib/analytics.js` 의 `captureUtm`).

## 5. 이 지표로 무엇을 결정하는가 — 미션 9-2 로 넘기는 질문

| 관측 | 그때 검토할 개선 |
|---|---|
| 상세 열람률이 낮다 | 목록 카드에 급여·지역을 더 드러낸다 |
| 로그인 통과율이 낮다 | 지원서 먼저 작성 → 제출 직전 로그인으로 순서를 바꾼다 |
| 지원 완주율이 낮다 | 지원서 입력 칸을 줄인다 · 임시저장 |
| AI 초안 채택률이 낮다 | 입력 힌트를 늘린다 · 실패 문장을 고친다 |
| 특정 채널의 지원 전환이 유난히 높다 | 그 채널에 소재를 더 만든다 |

⛔지금 이 표의 오른쪽을 실행하지 않는다 — **관측 없이 고치면 무엇이 효과였는지 알 수 없다.**

## 6. 측정에서 «빼는» 것

| 빼는 것 | 이유 |
|---|---|
| 제작자 본인의 접속 | 소수의 방문에 제작자가 섞이면 전환율이 통째로 흔들린다 |
| 검증용 반복 접속 | 화면 확인 때마다 「신규 방문자」가 늘어난다 |
| 식별 정보(이메일·이름·연락처) | 분석에 필요 없다. 누가 지원했는지는 지원 내역이 안다 |

★마지막 항목은 **설계 원칙**이다 — 이벤트 속성에는 「길이·여부·분류」만 싣는다.
