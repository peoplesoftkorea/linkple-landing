## 1. 선택한 고도화 기능 — OpenAI API 활용: 「AI 공고문 작성 도우미」

세 선택지(유저 기능 / 결제 기능 / OpenAI API) 중 **OpenAI API 활용**을 선택한다.

### 1-1. 기존 MVP의 어떤 한계를 보완하는가

미션 7까지의 Linkple은 공고를 **등록·탐색·지원**하는 흐름이 완성돼 있다. 그런데 실제
사용 장면을 상상하면 공급측(공고를 올리는 사장님)에서 흐름이 막힌다:

- **공고 등록 폼(JobNew)은 제목·본문을 전부 직접 써야 한다.** 채용 공고문은 쓰는 사람이
  익숙하지 않은 글쓰기다 — 무엇을 적어야 지원자가 오는지(업무 내용·조건·우대사항의 구성)를
  모르는 채 빈 텍스트박스를 마주한다.
- 결과: 공고의 **품질 편차**가 크고, 빈약한 공고는 지원으로 이어지지 않는다. 공급측 마찰은
  플랫폼 전체(탐색·지원)의 가치를 깎는다.

**AI 공고문 작성 도우미**는 이 한계를 정면으로 보완한다: 사용자가 핵심 사실 몇 가지만
입력하면(직무·근무지·조건·특이사항) AI가 구조를 갖춘 공고 초안을 만들어 폼에 채워 주고,
사용자는 **고쳐서 등록**한다.

### 1-2. 다른 두 선택지를 고르지 않은 이유

| 선택지 | 판단 |
|---|---|
| 유저 기능 | 미션 7에서 이미 JWT 인증(bcrypt 해시·토큰 만료·보호 API·401/403)을 구현했다. 여기에 더 얹는 것은 「지금 반드시 필요한 기능」이라기보다 인프라 고도화다. |
| 결제 기능 | 현재 MVP에는 **결제할 대상이 없다**(무료 공고·무료 지원). 결제를 넣으려면 유료화 시나리오부터 지어내야 해서, 기존 흐름과 연결된 설계라는 미션 요구와 어긋난다. |
| **OpenAI API** ✅ | 기존 흐름의 실제 병목(공고 작성)을 보완하고, 서버 측 API 프록시·키 보호·로딩/에러 UX까지 미션의 심화 요구사항을 자연스럽게 전부 지나간다. |

### 1-3. MVP 관점의 최소 기능 범위

**넣는 것 (이번 미션)**
- 공고 등록 화면의 「AI 초안」 패널: 입력 4칸(직무 / 근무지 / 근무조건 / 강조할 점) → 초안 생성 → 폼 자동 채움
- 서버 엔드포인트 `POST /api/ai/draft` 1개 — **로그인 사용자만**(미션 7 JWT 재사용)
- 로딩·에러·재시도 UX, 입력값 검증, 토큰 상한

**빼는 것 (의도적 단순화)**
- 스트리밍 응답 — 공고 초안은 3~5초 내 한 번에 받는 편이 폼 채움 UX와 맞다. 복잡도 대비 이득 없음
- 대화형 수정("더 친근하게 바꿔줘") — 초안 재생성 버튼으로 갈음
- 지원자 쪽 AI(자기소개 초안 등) — 확장 후보로만 남긴다 (§5)

## 2. 기능 설계 및 흐름 정의

### 2-1. 기존 서비스 흐름 속의 위치

```
[기존 흐름]  로그인 → 공고 등록(JobNew) → 공고 목록(Jobs) → 상세(JobDetail) → 지원 → 지원 내역
                          ▲
[이번 미션]               └─ 여기(공고 등록 화면 안)에 AI 초안 패널이 들어간다.
                             새 화면을 만들지 않는다 — 기존 흐름이 깨질 자리가 없다.
```

### 2-2. 사용자 기준 시나리오

| 질문 | 답 |
|---|---|
| **언제 쓰는가** | 로그인한 사용자가 공고 등록 화면에서 「AI로 초안 만들기」를 펼쳤을 때 |
| **무엇을 입력하는가** | 직무(필수) · 근무지 · 근무조건(시급/시간대) · 강조할 점 — 문장이 아니라 **단어 수준** 입력 |
| **무엇을 얻는가** | 제목 + 구조를 갖춘 본문(업무 내용 / 근무 조건 / 우대·특이사항)이 **폼에 채워진 상태**. 그대로 고쳐서 「등록」 |

실패 시나리오도 흐름의 일부다:
- 직무 미입력 → 클라이언트에서 즉시 안내(요청 자체를 보내지 않는다)
- 미로그인 → 401, 기존 미션 7 규약대로 로그인 화면 유도
- OpenAI 오류·타임아웃 → "초안 생성에 실패했습니다. 다시 시도하거나 직접 작성해 주세요" — **AI가 죽어도 수동 작성 경로는 항상 살아 있다** (기능 실패가 기존 흐름을 막지 않는다)

### 2-3. 아키텍처 — 키는 서버에만 있다

```
브라우저 ──(JWT + 입력 4칸)──▶ /api/ai/draft (서버리스 함수)
                                  │  ① JWT 검증 (미션 7 미들웨어 재사용)
                                  │  ② 입력 검증·길이 상한
                                  │  ③ OpenAI Chat Completions (JSON 응답 강제)
                                  ◀─ { title, body }
```

- `OPENAI_API_KEY`는 Vercel 환경변수로만 존재. 클라이언트 번들에 절대 실리지 않는다
- 응답은 JSON 스키마(제목/본문)로 강제해 파싱 실패를 구조적으로 막는다
- `max_tokens` 상한 + 입력 길이 상한으로 비용·오남용을 이중으로 제한

### 2-4. 기술 선택의 이유 (심화 요구사항 대응)

- **서버 프록시 방식**: 키 보호가 첫째 이유. 둘째로 검증·상한·로깅을 서버 한 곳에 모을 수 있다
- **비스트리밍**: 결과가 폼으로 들어가는 UX라 부분 출력이 의미 없다. 단순한 쪽을 의도적으로 선택
- **인증 뒤에 두기**: 익명 호출을 열면 비용 공격면이 된다. 미션 7의 JWT 게이트를 그대로 재사용 — 기존 MVP와의 통합이 곧 보안 설계가 된다

설계 단계에서 세운 검증 계획을 배포본(`https://linkple-mission8.vercel.app`)에 그대로 돌린 결과다.
판정은 문서 서술이 아니라 **실제 응답**으로 한다. (실측 2026-09-21)

| # | 검증 항목 | 기대 | 실측 결과 |
|---|---|---|---|
| 1 | 서버 기동 | `GET /api/health` 200 | ✅ 200 |

| 5 | 미로그인 차단 | 토큰 없음 → 401 | ✅ 401 |

- 성공 경로: 4칸 입력 → 초안 폼 채움 → 수정 → 등록 → 목록·상세에서 확인 — **기존 흐름 무결**
- 실패 경로: 필수 미입력 / 미로그인 401 / AI 실패 시 안내 문구 — 각각 의도한 화면 확인
- **키 노출 점검**: 공개 저장소 푸시 전 `sk-` 패턴·키 대입 전수 스캔 0건 · `.env.example`은 빈 값만
- **시간예산**: 서버리스 함수 제한(10초) 안에서 실패 문장이 나가도록 AI 호출 예산을 8초로 두고 자동 재시도를 제거했다 — 침묵하는 타임아웃보다 말하는 실패가 낫다

## 5. 확장 가능성 (구현하지 않되 막아두지 않는다)

- 지원자 쪽 AI(자기소개 초안) — 같은 `/api/ai/*` 프록시 패턴으로 엔드포인트만 추가
- 공고 요약·매칭 추천 — 프롬프트와 응답 스키마만 다른 동일 구조
- 사용량 증가 — 서버리스라 수평 확장은 플랫폼 몫, 남는 것은 비용 상한(입력·토큰 상한이 이미 그 자리)
